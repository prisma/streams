# O5 source candidate: complete encrypted canonical intervals

Status: disabled experimental candidate. Source and performance acceptance remain open. `EXPERIMENTAL_CANONICAL_SPAN_CACHE=1` selects it explicitly. The validated configuration requires at least 2 MiB of `HISTORY_CACHE_BYTES`; enabling it deducts exactly 2 MiB from the existing Foyer block-cache capacity. The default remains disabled. Foyer retains its block role; it does not provide this exact-interval proof or tenant/lifetime accounting.

A ready entry proves that one canonical scan reached EOS over the exact `[from,to)` below the captured remote-durable absorbed frontier. It contains every structurally checked encrypted row, including filtered misses, and therefore proves negative space between those rows. Cache hits run the same scan-byte admission and exact-key selection policy as misses. Presented-key authentication, decompression, plaintext admission, current authorization and descriptor resolution remain request work. The cache stores neither plaintext nor an authorization result. Structurally valid ciphertext with an invalid AEAD tag still fails authentication on every response.

`ReadPlan::for_descriptor` carries the descriptor to the physical history boundary. The cache binds its project, epoch, physical segment and route to the live engine and that engine's current history Db opening. Both weak opening identities remain unique while a scope exists. Unscoped low-level probes bypass the candidate. HTTP, fork, frozen scan, peer scan and SSE plans use the same descriptor binding; unfiltered canonical scans deliberately remain outside the candidate.

One cache mutex serializes exact-interval lookup, pending registration, installation, project invalidation and retirement. A fill ticket must still own its exact pending identity and a live generation to publish. Matching hits check their own owner/generation; unrelated closed entries are reaped on miss/admission. Drop, oversized capture, a truncated scan, scan error, invalidation and retirement all release that pending entry and wake identical-fill waiters. A waiter makes one retry after waking and can bypass to canonical storage; it cannot wait indefinitely on a dropped producer. In-flight scans are ordinary cancellation-safe futures.

The accepted retirement transaction handoff is unchanged. `ShardEngine::begin_close` calls cache retirement immediately after that handoff publishes the closed flag. A cache admission that observes the flag is refused; already admitted immutable bytes may finish their reader lifetime. An independently closed history Db is rejected through a temporary status subscription at lookup and installation. Scopes retain no status receiver that could pin a dropped database’s manifest. The executor also checks that the scope matches its actual database and namespace arguments. Project invalidation runs after the actual delete transition and the fork-reference cascade. Current soft-delete/expiry authorization and legitimate retained ancestor reads still follow the existing descriptor rules. Physical history is append-only below absorption today: any future destructive canonical retention must invalidate before removing rows. Project-policy checks remain independent of ciphertext reuse; caching is not a policy lease.

## Allocation and admission

Predeclared limits are 2 MiB globally, 256 KiB per project, 256 total ready/pending slots, 32 live project quota slots, 64 KiB fixed metadata, and a 64 KiB maximum per pending fill. Fixed tables have no growth path. Fixed metadata has a construction-time size check plus a conservative control/header allowance. Per-request scopes and pending signals reserve 512 bytes each before allocation. A full table or unavailable allowance gives bounded canonical bypass, rather than waiting for memory.

Each fill reserves data and control capacity together before retaining any frame. Its credit comes from the planned stored bytes and maximum possible row count, capped at 64 KiB; actual retention is checked before every allocation. Underestimates abandon caching and preserve canonical delivery. Pending fills cannot force eviction of ready entries merely to satisfy temporary reservation pressure. It immediately copies backend slices into exact-size owned storage; an SST allocation cannot hide behind a small cache slice. The fill bound includes old/new vector growth and final boxing transients. On EOS, exact boxed byte lengths and checked-frame array size plus conservative ownership headers determine the retained charge. A completely empty proof also retains its reservation.

`retained_bytes::with_charge` is shared with the admitted plaintext batch. Cache byte aliases carry the same reservation as their immutable frame owner. Eviction, project invalidation and producer return cannot release the charge while a reader still holds even a one-byte slice. The reservation retains the project quota object itself, so a weak project-table slot cannot create a second quota while old bytes survive. Tenant exhaustion evicts only that tenant's ready entries; global pressure may evict other ready entries. Pending work is never silently displaced for a newer fill.

## Validation scope

Deterministic tests cover cold/warm exact records, misses and empty intervals, wrong-key authentication on a warm result, independent requested budgets, malformed stored rows, oversized spans, withheld records, cancellation, identical-fill waiting, project generation changes during held fills, engine retirement, independent Db close, descriptor/route/incarnation/runtime mismatches, weak quota-table churn, global fill pressure and last-alias release. The HTTP fixture additionally drives real append/absorption, keyed reads, wrong-key rejection, delete invalidation and recreate isolation.

These tests and accounting assertions are source evidence. They do not establish fleet latency, process RSS parity, independent cryptographic approval or deployment approval. Matched native System/mimalloc screens and the final source gates are recorded separately when executed.
