# O4: immutable postings windows

Experimental; performance and correctness acceptance pending. Control: O1 + O3 (`05c0d939d25e8cc425c7a7c6f7fc3bbf05c88503`).

A warm cache hit now retains the existing immutable `Arc<[AbsRun]>`, binary-searches both overlapping boundaries, and exposes clipped values through an iterator. Both temporary clipping vectors and helpers are deleted. The existing planner consumes the iterator; its span, amplification, byte and progress logic is unchanged. Cold loads still allocate their admitted run owner. Boundary byte estimates retain whole-run matching/gap bytes.

The differential regression compares old double clipping against the new window over 40,960 deterministic sparse/dense, empty, partial-coverage and budget combinations, including every resulting plan field. A 100,000-run case proves a late window addresses just its three overlapping runs and preserves conservative estimates. Existing malformed-index and warm-window invalidation tests remain gates.

This saves two temporary vectors on warm reads but retains an Arc to the cached owner until planning finishes. It does not add cache residency or change cache budgets. Small fixtures may show little latency improvement; algorithmic scaling and latency acceptance are separate conclusions.

The run-window owner is explicitly dropped immediately after synchronous planning, before any canonical scan awaits. This prevents an evicted large postings array from remaining pinned throughout backend I/O.

Experiment completed: mechanism verified; performance acceptance remains limited as recorded in the [results](results.md) and [ledger](ledger.md). These notes describe the implementation, not a shipping-performance certificate.
