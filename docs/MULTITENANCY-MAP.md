## identity and hash derivation (segmap, shard, sharddir, postings, postings_cache, touch_keys, crypto, registry, sketch, scaler3 + their derivation roots/callees)

Every storage-facing identity in this area descends from one root: crypto::stream_hash over a bare string. Route hash = stream_hash(name); storage hash = stream_hash(name+"\0inc\0"+epoch); segment identity = stream_hash(name+"\0segid\0"+id+"\0"+epoch); split-child routes = stream_hash(name+"\0segroute\0"+child+"\0"+salt). These four constructions (registry.rs and scaler3.rs) are the conversion chokepoints — postings keys, history-v2 keys, engine keyspace keys, postings-cache keys, segmap route_hash fields, tail-row route16, and AES-GCM frame AAD all consume the resulting 16-byte values transitively and need no per-site logic change, only the v4 fresh namespace. The genuinely name-keyed surfaces that need direct rework are: the registry path scheme (registry/by-name/<hex(name)>), the registry descriptor cache and its entire name-string API, the global catalog listing + bare-name cursor, persisted ForkRef.source, the dead segmaps/<hex>.json ops-bucket persistence, and the scaler's three process-global maps (sketches, cooldowns, hot keys) keyed by bare stream name. touch_keys, sketch.rs, and sharddir.rs were read and verified identity-neutral (user-data or cell-infrastructure scoped); touch_keys is additionally a normative cross-language SDK contract that must NOT gain a project input.

**Risks / subtleties:**

- Frame-AAD coupling: every stored and wire record binds the 16-byte segment identity as AES-GCM AAD (crypto.rs aad; committer at shard.rs:3032), and deterministic re-encryption (byte-immutable chunks) depends on those exact bytes. The v4 identity change makes all v3 ciphertext undecodable under v4 identities — intended for the clean switch, but the preview export/reimport path and src/bin/keys.rs must explicitly decrypt under old identity and re-encrypt under new, never mix.
- Newtype discipline must survive the conversion: RouteHash vs SegmentHash vs RoutingKeyHash exist because a bare [u8;16] swap silently corrupted the absorb-lag join and would corrupt adjacent hist2/postings key slots (crypto.rs:146-177 docs). A project-qualified rewrite that funnels everything through one generic 'tenant hash' helper reintroduces that bug class; keep three distinct domain-separated constructors.
- touch_keys.rs is a normative cross-language contract (SDKs derive table/template/watch keys offline via WebCrypto SHA-256). Adding project_id to those hashes breaks every client; segmap::key_point shares the same construction. Tenancy must bind at journal/stream scope and URL auth only. A blanket 'no stream_hash without project' CI grep (stage 3 checklist) needs explicit carve-outs for routing-key/user-data hashing.
- Registry cache aliasing: the descriptor cache (registry.rs:506) and the scaler's sketches/cooldown/hot-key maps (scaler3.rs:102-107) are process-global and keyed by bare name. If API conversion and cache-key conversion don't land atomically, one project can be served another's descriptor (key fingerprint, epoch, segment map) or inherit its scaling heat/cooldowns — cross-tenant data exposure, not just a correctness nit.
- Persisted formats that embed name-rooted values: SegmentDesc.route_hash inside descriptor JSON, tail-row v3 trailing route16 (encode_tail/decode_tail), ForkRef.source bare name, and postings/hist2 key bytes. None change shape, all change meaning at v4; the layout gate (decode_desc + LAYOUT_VERSION) is the only thing preventing v3 bytes being interpreted with v4 semantics — extend the same gate discipline to any non-descriptor object family (segmaps/*.json is currently ungated and apparently dead: delete it).
- Catalog cursor is a wire format: CatalogPage.next_after is a bare name echoed to clients and fed back as the listing offset. Plan §10.3 requires project_id + last_name + cursor_version with invalid_cursor on cross-project reuse — a plain string cursor survives conversion silently and becomes a cross-project probe primitive if unversioned.
- Zero-route fallback is a residual deployment-global assumption: AppendReq.route zeros are accepted ('some DST paths', shard.rs:686-691) and tail decode defaults route to zeros. Under multitenancy an unroutable zero entry is also un-attributable; either forbid it outside DST or the v2 keyspace accumulates project-less rows that can never range-split or be billed.
- DST determinism: dst.rs and dst_tests derive key hashes and identities from fixed name strings (stream_hash(rk), fixed [u8;16] literals); the domain-separated project-qualified constructions re-randomize every simulated keyspace, shard placement, and split point. Expect DST scenario goldens and any seed-pinned repros to shift at stage 3 — plan a one-time re-baseline, and give the DST harness an explicit project fixture instead of relying on hash stability.
- Shard placement redistribution: shard_for_hash consumes the leading bits of the route hash, so project qualification re-randomizes stream→shard-prefix assignment. Safe only because v4 namespaces are fresh; any tooling that pre-computes prefixes from names (scripts, runbooks, src/bin/* helpers) breaks silently.
- The 0xFF DIRTY_SENTINEL index and shard maintenance rows (shard.rs:183-260) deliberately sort outside every route range; with multiple projects per shard they become tenant-mixed. Fine for static handoff, but the documented future range-split needs a route-local (now project-qualified) representation before splits land — the conversion should not entrench the sentinel further.
- Ops/audit identity: scaler transitions emit journal events keyed by (epoch, name) (scaler3.rs:778-784, 825-831) and observability strings like hot_keys 'name:hexprefix' (stats_json). Without project qualification, same-name streams in one cell alias in the topology journal and operator surfaces — stage 7 audit identity should be planned alongside the stage 3 hash switch so event dedup keys never span projects.
- Legacy remnants inflate the surface: SegmentDesc.shard_prefix (legacy child-stream scaler placement), segment_route's stream_hash(shard_prefix) arm, and segmap.rs load/save are dead or near-dead name-rooted paths. Converting them wastes effort and preserves aliasing hazards; deleting them in stage 3 (they're already flagged from the routing-v3 'legacy removal' chip) shrinks the checked conversion inventory.

## registry layout and catalog

The registry is entirely bare-name keyed today: descriptor paths are registry/by-name/{hex(name)}.json, the descriptor has NO project/tenant/workspace field anywhere (the deployment IS the tenant — one global bearer token in http::authorized), the in-process descriptor cache is HashMap<String(name)>, every Registry API (get/create/recreate/update/cas_update*/mutate_incarnation/invalidate/list_page) takes &str name, and all route/storage/segment identities root in crypto::stream_hash over delimiter-concatenated bare-name strings ("{name}\0inc\0{epoch}", "{name}\0segid\0{id}\0{epoch}"), with no domain separation or length prefixing. The catalog (GET /v1/streams → product_list → list_page) scans the single global prefix and its pagination cursor is unauthenticated base64 of the raw last stream name. Product cursors/tokens (KeyCursor/ScanCursor/MessageId/LeaseToken) bind stream epoch + customer key only, never project. LAYOUT_VERSION=3 with a hard decode gate is the clean-switch hook; v4 must add mandatory project_id to StreamDesc, project-prefixed paths, TenantStreamRef cache keys, project-scoped list_page, project-bound catalog cursors, and domain-separated length-prefixed hashes.

**Risks / subtleties:**

- Cache-key aliasing is the sharpest edge: Registry.cache is keyed by bare name with ETag revalidation, so under shared cells two projects with the same stream name would be served each other's descriptor, key fingerprint, and epoch; the key must become TenantStreamRef in the same commit as the path change, and all ~25 invalidate() call sites audited — a missed one silently serves stale descriptors rather than failing.
- The desc_path hex encoding is load-bearing for pagination: provider key order must equal stream-name order (list_with_offset continuation). The v4 template registry/v4/projects/<project-hex>/streams/<name-hex>.json preserves this within a project, but list_page's capped walk (limit*8+64 scan cap) and offset construction must be provably unable to iterate past the project prefix into a neighbor's namespace.
- Catalog cursor wire format changes from base64(raw name) to a versioned project-bound token: all outstanding cursors break (acceptable under the clean switch) but the decoder must classify old tokens as invalid_cursor, and reuse-in-another-project must be an explicit test (plan §10.3 and §19 Identity tests).
- stream_hash concatenates components with NUL delimiters inside format! strings ("{name}\0inc\0{epoch}", "{name}\0segid\0{id}\0{epoch}") — no length prefixing, no domain tags. The plan's §2.1 canonical encoding (u32-BE length + bytes, domain-separated route-v1/storage-v1/segment-v1) must replace every one of these; keeping delimiter concatenation with project prepended would leave cross-component ambiguity (a project id or name containing the delimiter aliases another tuple).
- Changing the route-hash derivation redistributes every stream across shard prefixes (shard_for_hash bits) and changes every storage/segment/usage/history-v2 key. Fine under the no-compat clean switch, but external mirrors must move in lockstep: src/bin/pilot.rs:99 reimplements hash_bits/shard_for_hash, src/bin/s3lite.rs:109 classifies keys by the literal 'registry/' prefix and 'topology.json', and fleet handoff/restore tooling assumes the current layout.
- DST determinism: src/dst/dst_tests.rs has 322 bare-name registry call sites; converting API signatures and hash inputs shifts shard placement, object keys, and interleavings, so DST seeds/goldens regenerate wholesale — plan for a one-time re-baseline, and add same-name-two-projects scenarios (the cache and CAS fences have never been exercised under name collision).
- Product tokens (KeyCursor/ScanCursor/MessageId/LeaseToken) bind project only transitively through the random per-incarnation epoch and the customer-held stream key. That is probably cryptographically sufficient, but it is implicit; if the review demands explicit project binding, the KIND version bytes and fixed-width length checks all change, and in-flight consumer leases are invalidated — this must ship inside the layout-4 cutover, never as a follow-up.
- ForkRef.source is a bare stream name persisted in descriptor JSON and hashed into create_request_hash; after conversion it must be interpreted strictly within the descriptor's own project, and the fork/create paths must reject cross-project sources BEFORE installing references or InitState (plan §1.4) — a replayed create's request_hash is project-blind, so path scoping is the only thing preventing cross-project replay joins.
- decode_desc gains a second corruption check (descriptor.project_id/name vs path) beyond the layout gate; get(), list_page(), and the CAS loops all decode — the mismatch error must fail closed everywhere, including the list_page walk where today an undecodable descriptor aborts the whole page (decide: skip-and-continue past a corrupt neighbor vs fail the page, since one tenant's corrupt object must not DoS another tenant's catalog... note list_page currently errors the entire page on any undecodable descriptor, which under shared prefixes was fine but under per-project prefixes is already isolated).
- Registry::list (unpaginated, deployment-global) has zero production callers — delete it during conversion; converting it faithfully would preserve a cross-tenant enumeration primitive nobody uses.
- The seal/init/consumer-saga fences (cas_update_incarnation, mutate_incarnation) reason about ABA via (name, epoch); post-conversion the fence tuple is (project, name, epoch) and every saga journal or step that persisted a bare name (consumer deletion fan-out targets, plan §16 InternalStreamTarget) must carry project_id or a takeover could act on another project's same-named stream.

## consumer/producer/fork/DLQ/watch durable state — src/queue.rs, src/offsets.rs, src/touch.rs, src/product.rs (consumer groups, producer sessions, forks, DLQ, watches), src/registry.rs (fork refs, watch definitions)

Every durable consumer/producer/queue row in this area is keyed by a 16-byte hash rooted in exactly three registry.rs derivations — StreamDesc::storage_hash (name+epoch), dynamic_segment_identity (name+seg+epoch), and stream_hash(name) route hashes — none of which include project_id; the queue.rs/shard.rs row builders (cursor/lease/ack/config/fence/producer rows) take that hash opaquely, so they convert automatically once the three roots become the domain-separated storage-v1/segment-v1/route-v1 hashes of stage 3, but their persisted rows change value, which is the layout-4 clean switch. The sites needing explicit code changes are the by-NAME references: ForkRef.source (persisted in descriptor JSON), ConsumerConfig.dead_letter_stream (persisted in the shard-DB config row) plus its three name-based resolutions (config-time validation, delivery-time re-resolution, DLQ append), the four internal-RPC sender/receiver pairs that put the bare stream name in peer URLs with no project in InternalTarget, the name-keyed registry path/cache that all fork/DLQ/consumer/watch lookups resolve through, and the watch observation URL whose persisted sig verifier binds only (stream key, epoch, watch-key) and must be replaced by the §15 project/method/expiry-bound capability. In-memory-only state (TouchRegistry journal map, Registry descriptor cache, QueueState/producers maps, http key cache) is a cache-key change that inherits the new hashes. Wire tokens that bind stream_epoch (consumer version token, MessageId/LeaseToken/KeyCursor) need no format change because the epoch is a random per-incarnation 16-byte value. src/offsets.rs contains no identity inputs at all (its "epoch" is the segment ordinal) and needs no changes.

**Risks / subtleties:**

- Persisted vs in-memory split: shard-DB rows (queue cursor/lease/ack/config/fence rows, producer sessions, seq rows), descriptor-JSON fields (ForkRef.source, watch_sig_key, watch_definitions), and DLQ record payloads (sourceStream) are PERSISTED and change only via the layout-4 fresh-namespace switch — no rewrite path exists, so any hash-derivation site missed at stage 3 silently aliases two projects' same-named streams onto one keyspace with no error. In-memory keys (TouchRegistry.map, Registry.cache, QueueState.consumers, http key cache, engine handle maps) inherit automatically but name-string-keyed caches (Registry.cache) will silently serve cross-project hits until re-keyed to TenantStreamRef.
- Three distinct hash domains share the bare [u8;16] shape (RouteHash, SegmentHash, RoutingKeyHash) and all currently funnel through crypto::stream_hash; the conversion must project-qualify route-v1 and storage-v1/segment-v1 but MUST NOT touch RoutingKeyHash / key_point (user routing-key data feeding per-key FIFO, postings, sketches, split points) — resolve_segment computes both within five lines, making this the highest-risk mixup site.
- touch.rs close_shard matches shard bit-prefixes (route-hash space) against journal keys (storage-hash space) — an existing domain mismatch that the conversion will perturb; decide the correct keying deliberately rather than inheriting whichever hash changes first.
- Wire formats that should NOT change: consumer version tokens and MessageId/LeaseToken/KeyCursor/ScanCursor bind the random per-incarnation stream_epoch under a stream-key MAC and are already globally unique across projects; gratuitously adding project_id breaks SDK compatibility for nothing — instead prove isolation via the §19 same-name-two-projects tests.
- ForkRef.source and ConsumerConfig.dead_letter_stream store bare names that become implicitly project-relative: preview-data export/reimport (the §1.5 migration story) must rewrite or re-anchor these embedded references, and same_identity / the 'd == name' DLQ self-check must be understood as project-scoped comparisons after conversion.
- Internal RPC conversion is a fleet wire-format change (sender URL/headers + receiver verification in the same release): during a rolling deploy a new receiver must reject project-less targets rather than defaulting, or the ABA protection §16 adds is void; the fleet-wide bearer today authorizes ANY name, so project verification is also a privilege reduction that consumer deletion, pull relays, and scan relays all depend on.
- Watch capability redesign invalidates every issued signed URL (persisted watch_sig_key verifier survives but the sig input set changes) and the derivation chain is a NORMATIVE cross-language contract mirrored in sdk/src/index.ts — server and SDK must switch in lockstep, and the new expiry/method binding ends the 'immutable, CDN-cacheable forever' property the current design exploits for cohort collapse; the CDN caching story needs an explicit answer for capabilities with 5-minute lifetimes.
- DST determinism: project-qualifying storage/segment/route hashes changes every DST seed's shard placement, engine identities, queue keyspaces, and split points — golden traces and any test deriving expected hashes from names must be regenerated, and the DST harness needs multi-project cases or stage-3 regressions (e.g. a missed name-only derivation) stay invisible in single-project runs.
- Registry catalog scans (list_page/list_page_raw/list over 'registry/by-name') are deployment-global and feed both the product catalog and billing reconcilers; they must become per-project prefix walks, and the product_list continuation cursor (base64 of the bare last name) must bind project_id + cursor_version per §10.3 or a cursor replays across projects as a different project's listing position.
- The deletion saga's correctness today leans on random epochs to break name ABA; after conversion the epoch pin AND project pin are both required (a project transfer does not change project_id, so sagas survive transfer, per §1.1 — worth an explicit test that transfer mid-saga neither aborts nor misbinds it).

## internal RPC and fleet API (src/fleet.rs, /v1/internal/* routes in src/http.rs, fan-out senders/receivers in src/product.rs, system-stream client + lifecycle walk in src/billing.rs, committer/engine callers in src/shard.rs, FLEET_INTERNAL_TOKEN wiring in src/main.rs)

The internal RPC surface is five bearer-gated routes (/v1/internal/segment-read, sweep-segment, queue-cursor, segment-scan, telemetry-append) all keyed by a bare canonical stream name in the URL path ({*name} wildcard), with incarnation binding (MF2) carried in three headers via product.rs InternalTarget: streams-internal-epoch (hex stream_epoch), streams-internal-seg (u32), streams-internal-identity (hex 16B, dynamic_segment_identity = hash over name+seg_id+epoch — no project). Receivers do a bare-name registry.get(name), then verify_internal_target re-derives epoch/segment/identity from whatever descriptor owns that name. Versus the plan's InternalStreamTarget {project_id, stream_name, stream_epoch, segment_id, segment_identity}, the wire today has name+epoch+segment_id+segment_identity but NO project_id anywhere, and telemetry-append has NO incarnation binding at all (name-only, `_`-prefix gate). Authorization is a single static shared FLEET_INTERNAL_TOKEN (constant-time bearer compare, fail-closed) with zero target or operation binding — one credential authorizes every operation on every stream in the cell, which §14.1 replaces with workload JWTs + delegated per-operation capabilities. Peer discovery is instance-name → base-URL via bucket-writable fleet/<instance>.json heartbeats (SELF_URL) overridden by fleet/urls.json, filtered by valid_peer_url + FLEET_PEER_DOMAINS; Streams-Replay-To carries the owner instance name (physical — correctly workspace/project-free, no change needed to the ring/rebalancer/shard-prefix layer). Fan-out senders: relay_segment_read (lineage reads), relay_segment_scan + relay_segment_tail (scan pages/snapshots), relay_queue_cursor (pull walk), relay_sweep_segment (consumer-deletion saga, driven from product_consumer_delete with fence generation), system_append/system_read (telemetry relay to bare reserved names _usage/_ops_metrics/_ops_events, which must move to system/v1/cells/<cell-id>/). Billing attribution flows into internal paths via identity_of()'s deployment-global AppState.account_id/project_id fallback, persisted by the shard committer into SegmentBillingMetaV1, and the tombstone_walk lifecycle cleanup pages the registry deployment-globally. 30 sites mapped below.

**Risks / subtleties:**

- Mixed-layout fleet during cutover: streams-internal-identity and -epoch are re-derived independently on sender and receiver from the SAME hash recipe; if any instance computes pre-v4 (name-only) hashes while another computes project-qualified ones, every cross-owner RPC answers 409 stale_target and fan-out (lineage reads, pull walks, deletion sagas, telemetry relays) silently degrades to permanent bounce loops. The clean-switch rule must mean one atomic binary+layout generation per cell — the frozen-binary/one-incarnation-per-release posture already in place is the mechanism.
- URL grammar for the project: all five internal routes use a {*name} wildcard that swallows slashes (stream names may contain '/'), so adding the project as a path suffix is ambiguous; it must be a path segment BEFORE the wildcard (e.g. /v1/internal/projects/{project}/segment-read/{*name}) or a verified header inside the target struct — and whichever carrier is chosen must be covered by the delegated-capability signature or a peer can replay a capability against a different project's identically-named stream.
- internal_telemetry_append is the only internal endpoint with no incarnation binding and it authorizes CREATION by name prefix alone — any fleet-token holder can create arbitrary `_`-prefixed streams in the shared registry namespace with an attacker-chosen key. Moving system streams to system/v1/cells/<cell-id>/ must delete the name-prefix acceptance entirely, not layer on it.
- Shared FLEET_INTERNAL_TOKEN is a cell-wide skeleton key: one compromised instance can sweep (fence+delete) consumer state and read keyed segments for EVERY project. §14.1's delegated capabilities are a per-call-site change to all seven senders and five receivers; the capability must bind the same tuple verify_internal_target checks (project, stream, epoch, segment, operation) or the two checks can disagree.
- Customer stream keys cross the instance boundary in cleartext headers (relay_segment_read forwards stream-encryption-key/prisma-encryption-key; internal_segment_scan requires the key to decrypt remotely) to URLs sourced from a bucket-writable map. valid_peer_url + FLEET_PEER_DOMAINS is the only current barrier (round-19 finding); until peers prove workload identity, project-qualification alone does not close the exfiltration path.
- Cache keys and KeyCache aliasing: state.keys.put(identity, ...) and the registry cache key by name/identity-hash today; under two projects with the same stream name, any missed conversion (a cache keyed by bare name, or an identity hash still computed from name+epoch) is a silent cross-project data leak, not an error. The plan's CI grep for name-only identity derivation should specifically cover crypto::stream_hash call sites with format!-concatenated inputs (registry.rs storage_hash/dynamic_segment_identity/segment_route use NUL-delimited concatenation, which §2.1 replaces with length-prefixed components + domain tags).
- DST determinism and shard placement: route hashes feed shard_for_hash and ring_pick, so project-qualifying route-v1 changes which shard prefix and instance own every stream; recorded DST corpora, the rebalancer's lag keying (already once broken by the storage_hash-vs-stream_hash mismatch, fleet.rs pick_victim_shard comment), and soak baselines all invalidate on the switch and need regeneration, not migration.
- Telemetry cursor reset: rollup_step/ops_rollup_step cursors and the read-spool/outbox dedup state are positions in the OLD _usage/_ops_metrics streams; the namespace move must start fresh cursors and accept a clean cut in billing continuity (export/reimport for surviving preview usage), because deterministic event-id dedup only protects within one stream incarnation.
- Internal requests bypass metering and admission by design (ReadParams.internal = never metered, correct for double-counting) — but they also bypass any future per-project concurrency backstops; stage 6 quotas must count relayed work against the ORIGINATING project's admission or cross-owner fan-out becomes a quota-amplification loophole.
- Billing fallback removal ordering: identity_of's deployment-global fallback (acct_local/proj_local defaults in main.rs) is load-bearing for every existing dev/DST descriptor without account/project fields; making descriptor project_id mandatory (stage 3) before removing the fallback (stage 7) leaves a window where the fallback silently mislabels usage in shared cells — the two changes need a shared gate in tests.
- Wire-format compatibility of the target headers themselves: streams-internal-epoch/-identity are hex-encoded 16-byte values with no version tag; adding project binding via NEW headers keeps old receivers silently ignoring them (fail-open to name+epoch matching). The conversion should version the target (e.g. streams-internal-target-v2) so an unconverted receiver REFUSES rather than half-verifies.

## authentication surfaces (src/http.rs, src/product.rs, src/operator.rs, src/main.rs)

Every customer-facing auth decision today reduces to one deployment-global shared secret (AppState.auth_token via authorized()) that is all-or-nothing, project-blind, scope-blind, and fails OPEN when unset; a second shared secret (FLEET_INTERNAL_TOKEN) gates /v1/internal/*; the operator dashboard is deliberately unsecured; watch observation is a self-authorizing URL signature derived from stream key + epoch with no expiry, audience, method, or project binding; and the stream-encryption-key is the only per-stream credential, validated per-handler against a descriptor loaded by bare name. Tenant identity (account_id/project_id/cell_id) enters exclusively from deploy-time env and is stamped into descriptors and billing rows. Conversion: authorized()/product_auth_gate become RequestPrincipal middleware (Stage 2, separate customer/internal/operator/watch audiences), every bare-name registry/hash/key-cache lookup behind these gates becomes TenantStreamRef-qualified (Stages 3-4), watch URLs move to short-lived bound capabilities (Stage 4 §15), debug/operator routes move to an operator audience (Stage 2 §14.2), usage endpoints authorize through the project principal (Stage 7), and pre-auth admission/tarpit work moves behind authentication with per-project buckets (Stage 6).

**Risks / subtleties:**

- Fail-open default: authorized() returns true when AUTH_TOKEN is unset (http.rs:253) and product_auth_gate inherits this — every dev/DST/test harness relies on no-auth mode, so the Stage 2 fail-closed switch needs a fixture principal/issuer for the entire test battery (DST determinism: JWT verification must be injectable/clockless).
- Watch existence oracle: product_auth_gate passes any request whose query merely CONTAINS 'sig=' on a WatchWait-shaped path (product.rs:529-531), and product_watch_wait then answers 404 not_found/unknown_watch and 400 invalid_watch_key BEFORE verifying the signature (6061-6102 vs 6125) — an unauthenticated caller can enumerate stream and watch names today, and cross-project after the conversion unless capability verification moves ahead of the registry lookup or missing/invalid collapse to one uniform answer.
- Watch capability redesign breaks persisted format and offline derivation: watch_sig_key is stored in the descriptor at create (product.rs:879-886), URLs are deliberately eternal, and clients derive sigs offline from key+epoch (the exposed epoch at metadata_response:1035); §15's 5-minute expiry + project/method/audience binding invalidates issued URLs, changes the descriptor schema, and breaks any SDK doing offline derivation — needs an explicit flag-day story with layout 4.
- Watch sig lives in the query string with no log/trace redaction anywhere in http.rs/product.rs; §15 requires strict redaction — audit tracing/ops-event emission before shipping URL capabilities.
- Pre-auth capacity answers: track_inflight (http.rs:566) tarpits and 429s /v1/stream* requests before any authentication, contradicting §9 (auth before tarpit) — and its instance-global bucket merges all projects, contradicting §17.3; moving it post-auth changes the DoS posture of the unauthenticated path and needs its own review.
- Aliasing through name-only hashes at auth-adjacent sites: ring_owner_check/create_stream compute stream_hash(bare name) for routing before any project context exists (http.rs:2395, 2453), and usage counters/KeyCache/segment identities key off name- or storage-hash — until Stage 3 lands, two projects' same-named streams share route hashes, key-cache slots (state.keys.put(desc.storage_hash()) at product.rs:6168), and usage counters; Stage 4 surface conversion MUST NOT ship before Stage 3 hashes are project-qualified.
- Existence-revealing ordering on converted paths: append_core and read paths do the bare-name registry lookup (existence) before the stream-key check (http.rs:4476 vs 4498); post-conversion this is safe only if the lookup itself is scoped to the principal's project — otherwise 404-vs-403 differences become a cross-project existence oracle. Same for gone_or_missing's 410-vs-404 tombstone distinction.
- delete_stream requires NO stream key — the deployment bearer alone deletes any stream (http.rs:3402); in a shared cell an over-scoped token is one typo from deleting another team's stream, so the streams.lifecycle.manage + prefix-grant conversion of DELETE should land in the first Stage 4 batch.
- Customer-bearer debug surface mutates shared state: /v1/debug/absorb-pause, abort, history-stall, sleep occupy slots or change absorber behavior cell-wide under the CUSTOMER token (http.rs:1063-1141); under shared cells any tenant could degrade every other tenant — these must move to the operator audience in Stage 2, not Stage 4.
- Wrong-cell vs 401 semantics: today every auth failure is a uniform 401; §8.1 requires a valid token at the wrong cell to answer 421/503 wrong_cell, never 401 — the RequestPrincipal middleware must distinguish signature-invalid from wrong-cell_id claims or clients will refresh valid credentials in a loop.
- CORS preflight caching across the cutover: allow-headers lists are hardcoded in four places (http.rs:1470,1770; product.rs:614,616) with access-control-max-age 600; adding the Prisma-Watch scheme or renaming credential headers mid-rollout leaves browsers with stale preflights — version the header set with the SDK release.
- Fleet boundary (owned by another mapper, ordering note): relay senders forward the customer's encryption key plus the shared FLEET_INTERNAL_TOKEN and a project-less InternalTarget (http.rs:7117-7124, product.rs relay_*); receivers resolve by bare name — internal fan-out is a cross-project confusion vector until §16 project-qualified targets land, so internal RPC conversion cannot lag the public-surface conversion.
- debug_usage / ops events / operator payload discipline: cell-wide surfaces expose per-stream hashes, shard prefixes, and billing posture anonymously or under one bearer (http.rs:887, 953, 1539; operator.rs); the shared-cell external security review will treat any project-correlatable field here as a leak — re-audit payloads after project ids exist.
- product_usage's ?streamId= override (product.rs:6397) bypasses name-based identity to address arbitrary incarnation rows — must be bound to the principal's project in Stage 7 or it becomes a cross-project invoice oracle.
- consumer_version_token (product.rs:3897) is an unsigned client-held wire token pinning epoch+generation; it survives the conversion only because epochs are random — document this as a deliberate decision, and ensure the version-token-before-key ordering in product_consumer_delete (4796-4803) is preserved when the principal gate replaces the bearer gate.

## billing/usage/telemetry identity — src/usage.rs, src/billing.rs, src/rollup.rs, src/ops.rs (plus their identity roots in http.rs/main.rs/product.rs)

Billing identity today is deployment-global: AppState.account_id/project_id come from env ACCOUNT_ID/PROJECT_ID (defaults acct_local/proj_local), billing::identity_of() falls back to them for any descriptor missing tenant fields, and the usage API authorizes with the single deployment bearer AUTH_TOKEN plus a 'path project == state.project_id' string compare. **Risks / subtleties:**

- Money-correctness ordering hazard: drain_once's terminal-closure reconciler (billing.rs:1190) and tombstone_walk both resolve billing rows by BARE-NAME registry lookups guarded only by epoch equality. - Persisted-format blast radius: BillingIdentity/account_id is serialized into four durable places — shard-DB SegmentBillingMetaV1 rows, read-spool ReadBatch rows, the _usage ledger's JSON envelopes, and rollup v2 rows/keys. - Transfer vs captured identity: SegmentBillingMetaV1 captures the commercial owner 'at first append, immutable for the incarnation'. - Rollup keys are '/'-delimited string concatenations of unvalidated 1-128-byte ids, parsed back positionally with splitn (close_month, pending_artifacts). - Overflow coupling is a certified §17.3 violation: usage.rs merges every past-cap stream from all projects into one token bucket, and its traffic is deliberately unattributed ('accepted best-effort' pre-tenancy). - Hash-derivation ripple / DST determinism: converting stream_hash(name) → route-v1(project,name) changes shard selection (shard_for_hash), the usage-map keys, storage_links, and billing_meta_key inputs simultaneously; any DST seed corpus, precomputed test hashes, or recorded campaign artifacts keyed by old hashes silently stop matching. - Deterministic dedupe ids ('snap/{epoch}/...', 'life/{epoch}/...', 'read/{boot}/{seq}') rely on epoch/boot randomness for cross-tenant uniqueness rather than structural project qualification; changing id formats at cutover also resets dedupe floors — replaying any pre-cutover ledger page after the switch double-applies unless cursors are fenced at the boundary.
- Wire-format changes on internal RPC: /v1/internal/telemetry-append/{name} and the system_read segment-read relay are name-addressed; §16 requires InternalStreamTarget (project, name, epoch, segment id+identity) verified at the receiver. Old and new fleet members cannot mix across the cutover — matches the one-incarnation-per-release posture but must be stated in the rollout plan.
- Cross-tenant info disclosure pre-dating the conversion: /v1/debug/usage (and other debug surfaces behind the single AUTH_TOKEN) enumerate cell-wide per-stream counters and hashes; under shared cells these must be re-homed to operator/internal audiences (stage 2) BEFORE the first second tenant lands, not at stage 7.
- The month-close pipeline (close_months_due marker, per-month cursors, artifact-pending outbox) is stateful across the cutover: a rollup down over the switch will try to close pre-cutover months from post-cutover code against the new keyspace. The v3 rollup DB must start with an explicit oldest-unclosed marker at the cutover month, with pre-cutover months closed by the old binary or by an export job.
